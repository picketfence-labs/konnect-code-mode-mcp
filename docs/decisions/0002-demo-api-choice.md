# 0002. デモに使うAPIの選択（独自mock-api vs SE手順書のサンプルAPI）

- **日付**: 2026-09-04（事後再構成。判断自体はリポジトリ初期構築時、2026-07頃）
- **状態**: 決定

## コンテキスト
社内SE向け手順書（`Kong Operator Context Mesh - SE's.md`、Obsidian Vault
`01-Projects/2026-09_konnect-code-mode-mcp/notes/`参照）は、Context Mesh / Code Modeの
デモ用サンプルAPIとして「Flights API」（KongAirのサンプル、`Kong/KongAir`リポジトリのJWT等
一式が既に用意されている）と「Openweather API」（実在の外部APIキーが必要）の2つを提供している。

## 検討した選択肢
1. **Flights API（SE手順書のサンプル）**: セットアップが最も簡単（サンプルAPIをそのまま
   アップロードするだけ）。ただしデータ量・構造がシンプルで、「大量データをサンドボックス内で
   集計しトークン削減を実証する」という本デモの主目的（Top5集計等）を強く見せるには不向き
2. **Openweather API（SE手順書のサンプル）**: 実データで説得力があるが、外部APIキーの取得・
   有効化待ち（数時間かかる）という依存が生じ、再現性・自己完結性に欠ける
3. **独自のmock-api（気温データ、100都市×12か月×10年=12,000レコード）**: 外部依存が無く
   完全に自己完結。正規化された2エンティティ（`cities`/`temperatures`）構成により、
   「約100回のツール呼び出しを伴う集計」というCode Modeのトークン削減効果を分かりやすく
   実証できるデータ規模・構造を意図的に設計できる

## 決定
選択肢3（独自のmock-api）を採用した。

## 判断基準・根拠
- 本デモのゴールは「大量データに対する集計クエリでLLMトークン量が削減されることの実証」
  （`docs/design-brief.md`1章）であり、そのために必要なデータ規模・クエリパターン
  （約100回のツール呼び出し、正規化データの集計）を自由に設計できることを優先した
- 外部APIキー等の依存を避け、再現性・自己完結性を優先した（`docs/design-brief.md`5章の
  「外部依存先の前提条件確認」の観点にも合致）

## 想定していたこと vs 実際どうだったか
想定通り。独自データにしたことで「過去10年の3月の平均気温Top5」のような、集計の効果が
分かりやすいクエリ例を設計できた。一方、SE手順書のFlights/Openweather向けの手順
（Konnect UIでのMCP Server定義操作自体）は本デモにもそのまま応用できたため、
API選択の違いがKong Operator/Konnect UI側の手順に影響することは無かった。

## 影響・トレードオフ
- SE手順書のFlights/Openweather向け手順をそのまま流用できず、mock-api用のOpenAPI spec作成・
  デプロイ手順（`deploy/mock-api/`）を自前で用意する追加コストが発生した
- 一方で、外部APIキーの取得待ち等の外部依存リスクは無くなった
